# SEO page expansion plan

Date: 2026-11-03
Scope: proposed public routes for the RestaBee marketing site. This is a build sequence and content strategy, not a claim that routes exist. The keyword figures below are inherited from the supplied Google Keyword Planner export (1 Oct 2025–30 Sep 2026); they are rounded research buckets, not current SERP measurements or organic difficulty. See the preserved [keyword/page map](../master%20docs/RestaBee-SEO-Keyword-Page-Map.xlsx) and archived [website SEO strategy](../archive/RestaBee-Complete-Website-SEO-Launch-Strategy.md).

## Approach

The homepage and billing page now read SEO fields, primary copy, repeated content groups, pricing terms and FAQs from a validated Astro Content Collection. The existing Astro templates own page composition and design. Keep one primary intent per route, explain the operator task, use current product evidence and link to relevant pages and the demo form. Reuse supplied screenshots only where the pictured screen supports the page. Add no screenshots merely to fill a layout. Product screens contain sample restaurant data and are not customer proof.

After several pages are reviewable, revisit the homepage with the user. A likely move is the detailed My Shift / cash close material to a cash-management page. Do not remove or trim homepage sections before that review.

Follow the required [content and Astro authoring standards](../content-and-cms-standards.md) for each page. Model new page copy as validated, CMS-editable content and render it through reusable Astro templates. Keep each route’s custom visual composition and interactions in code.

## Conditional pages and content

- **Split billing:** initially explain eligible draft-check separation and split tender on the billing page. Split bills is ambiguous and has no strong validated standalone volume. Create `/features/restaurant-split-billing/` only if Search Console query evidence or user research shows distinct demand; distinguish splitting checks from splitting tender.
- **GST billing:** the map includes a restaurant GST billing page. Defer until the page can state precisely what configured tax profiles do and explicitly separate tax calculation/display from filing, certification and e-invoice integrations.
- **QSR, takeaway and cloud kitchen solutions:** each has modest reported volume (about 50). Build only with distinct workflows and examples that are supported by the product, not as location/vertical template pages.
- **Restaurant POS systems page:** the broad target overlaps the current homepage’s primary intent. Do not build a second generic page unless SERP evidence reveals a distinct full-service or system-comparison intent.
- **Table QR ordering page:** retain the current concise homepage section. The source strategy placed a standalone QR feature on hold pending end-to-end product acceptance. Reassess only after that evidence gate.
- **Demo, About and Contact pages:** plan them after the product-page sequence. The demo form needs deployed API/CORS confirmation; About/Contact facts need owner verification. Existing contact information should not be copied blindly.
- **Guides/blog:** enable the planned Markdown/CMS publishing workflow before adding articles. First candidates: restaurant POS cost in India (requires current dated sources), buying checklist, KOT guide, and KOT vs KDS. Keep informational guide intent distinct from product-page intent.

## SEO and publishing checklist for every page

1. Assign one primary query cluster and confirm intent against current search results before release; do not treat old volume buckets as forecasts.
2. Write a unique title, description, H1, opening answer, substantive workflow detail, FAQs and internal links. Measure the visible-main-body primary-keyword density against the 0.5% editorial floor; work toward 1% only where the wording remains natural.
3. Use self-canonical metadata, indexability, Open Graph/Twitter metadata, descriptive image filenames, accurate alt text and reserved image dimensions. Add only schema that describes visible, supported content.
4. Put released routes in the sitemap and `llms.txt`; verify all internal links, route metadata, one H1, image accessibility and static output.
5. Check sibling POS capability evidence and public pricing before publishing. Mark sample UI/data as illustrative. Recheck on-page copy after product or pricing changes.
6. Deploy only through the configured marketing-site workflow; verify the live route, canonical, sitemap and rendered mobile/desktop page separately from local build checks.

## CMS authoring requirements

- Define the page’s typed Content Collection schema, JSON entry and `.pages.yml` fields together before building its template. The build-time field-map check must pass for all fields.
- Use Astro Content Collections and build-time generation for static feature pages and blog posts. Keep route paths, layout, reusable section components, JSON-LD generation and shared navigation/footer under code review.
- Configure Pages CMS after the fields are modeled. Preview every CMS change with Astro checks and a production build before publishing.
- Design the page schema to accommodate the existing homepage and billing sections without changing their URLs or handing visual composition to editors.

## Why billing is first in the sequence

The restaurant billing page is built from the workbook’s commercial query opportunity and current bill/check/collection evidence. After this release, continue with pricing, the next route in the planned sequence, using the [page release gates](../content-and-cms-standards.md) from the first draft. Astro schema/content/Pages CMS field-map validation is required locally; the external Pages CMS account connection in L2 can be completed independently. The user authorized the specific pricing-copy correction and CMS content migration while preserving the homepage design. Keep the existing bill example and other sections in place until a later content move/trim review. The sample T3 bill on the new page is explanatory artwork, not a screenshot or real customer transaction.
